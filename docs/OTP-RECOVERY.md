Later `/verify` requests at 17:37:32 and 17:38:21 returned `403 One-time token not found`. The link is one-time use. The first visible page was the app's generic "Nothing here" route, and no `sb-...-auth-token` entry remained in Chrome local storage afterward. The exact reason the successful verification did not leave a durable browser session remains unproven; do not attribute it to a scanner without a controlled test.

The app now recognizes Supabase error fragments and offers a retry path. It also has an optional six-digit email code form for returning members using `verifyOtp({ email, token, type: 'email' })`. The code form only works after the hosted Supabase **Magic Link** email template includes `{{ .Token }}`. The repository's `supabase/email-templates/magic-link-code.html` is the exact candidate content. Hosted Supabase templates are not deployed by GitHub Pages or SQL migrations; an operator must apply this template in Supabase Dashboard > Authentication > Email Templates > Magic Link, with a subject such as "Your Open Labs sign-in code". Keep a copy of the old template until the controlled test passes. The sign-in request still uses `signInWithOtp` and does not require a separate endpoint.

Controlled test after applying the template: request one email for an existing test account, enter its six-digit code in the same browser without opening a confirmation link, and confirm the member screen appears. Then reload the clean site URL and confirm the session remains. Confirm a `sb-...-auth-token` key is present by key name only, never record its value. Finally sign out and confirm it disappears. If code verification succeeds but the app still shows Sign in, inspect the account's `public.profiles` row and the browser console/network error for `loadLive`; do not keep requesting codes.

The `Confirm Signup` template for new accounts is separate and is not changed by this recovery. Test returning-account sign-in first. Do not announce code sign-in as live until the hosted template has been applied and verified. The magic link can remain available until then.

## 2026-09-22 confirmed old-account failure and alternate verification path

This section supersedes the code-only template rollout above for the affected project.

A fresh code-only email was requested at 19:41:03 PDT and rejected by `POST /verify` 17 seconds later. The configured expiry is 3,600 seconds. Read-only SQL showed one confirmed `auth.users` row, one matching `public.profiles` row, a pending recovery token issued at 19:41:02, and an `auth.one_time_tokens` recovery row created at 19:41:03 with the same hash. A private hash comparison in Supabase SQL Editor returned `code_matches = true` for the emailed digits. The one-time-token row's `expires_at` was **null**. Do not record or share the digits or hashes.

Supabase Auth's current source treats a null `expires_at` as expired when its one-time-token source-of-truth path is enabled. This is the likely cause of the `POST /verify` 403, but the project's feature flags are not visible from this workspace. Do not edit `auth.one_time_tokens` directly; ask Supabase support to inspect the source-of-truth and expiry-write feature flags and include only timestamps, booleans, and the project reference.

The app now offers a two-step email sign-in route: the email links to `#/confirm-email/{{ .TokenHash }}`, and the visitor explicitly presses **Sign in to Open Labs**. The app then calls `verifyOtp({ token_hash, type: 'email' })`. Supabase's token-hash verification path uses the matching one-time-token row and the account's `recovery_sent_at` for expiry, so it avoids the null `expires_at` path. The exact hosted Magic Link template candidate is `supabase/email-templates/magic-link-confirm.html`. Apply that template in Supabase Dashboard > Authentication > Email Templates > Magic Link, replacing the code-only template, then request one fresh email. Verify the button signs in and a clean reload preserves the session. This workaround is not live until the hosted template is applied and tested.
